# 三套采用流程

## 复现多表订单故障

维护业务 SDK 的开发者已拿到 customers、orders、order_lines 的 JSON 导出，需要向同事提供可重放的故障样本。先列全表和全部列，声明订单链外键、主键、需要的唯一约束；给邮箱设置 token，给 ID 设置一致 reindex，给金额/时间选择 keep。运行 `check` 暴露原有孤儿行；修正导出后运行 `export`。接收方用同一策略 `verify`，通过库 `to_json()` 取出数据导入测试夹具。金额和时间保留原数值表示，联表关系被验证。全表实数据演示是 [Chinook](../examples/chinook/README.md)。

## 多租户回归测试

SaaS 维护者需要保留租户内部相同 account 编号，避免因样本脱敏把两个租户的数据合并。声明 `(tenant, account)` 复合主键和事件的完整复合引用；tenant 使用共享 token domain，account 使用共享 reindex 起点。转换前拒绝“两个分量分别存在、组合不存在”的跨租户引用。转换后重新检查整个元组；可空引用采用 MATCH SIMPLE。[多租户示例](../examples/tenants/README.md)可直接运行。CI 固定输入/策略/秘密和算法版本来保持结果稳定；不把当前批次映射当成跨批永久 ID。

## 交付可复核的 CI 样本

库维护者每次导出供集成测试使用的样本时，先审查 keep 列、选择独立高熵秘密，再 `export` 到新路径。一个 bundle 同时携带替换数据、行数报告、策略指纹和损坏检测摘要，省去人工对齐数据/报告版本。下游只需策略和 bundle，`verify` 后取出数据，不需要数据库服务、私有基础设施、原导出或秘密。路径已存在时换新名称；失败不覆盖已有样本。完整演练见 [导出契约](bundles.md)。

三套流程都依赖显式、完整的数据契约；未知列不会被悄悄删掉。当前不连接数据库、不解析 SQL dump、不自动识别敏感字段，也不保证未声明的业务 CHECK、触发器或任意查询行为。
